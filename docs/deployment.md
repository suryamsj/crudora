```bash

PORT=3000
NODE_ENV=production
```

For MySQL:

```bash

```

```json
// tsconfig.json
{

    "moduleResolution": "bundler",
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
```

## Basic Server Setup

```typescript
// src/server.ts
import 'reflect-metadata';
import { CrudoraServer, Model, Field } from 'crudora';
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import 'dotenv/config';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const db   = drizzle(pool);

class User extends Model {
  static schema    = 'auth';
  static tableName = 'users';
  static hidden    = ['password'];

  @Field({ type: 'uuid', primary: true }) id!: string;
  @Field({ type: 'string', required: true, unique: true }) email!: string;
  @Field({ type: 'string', required: true }) password!: string;
}

const server = new CrudoraServer({
  db,
  dialect:         'postgresql',
  port:            Number(process.env.PORT) || 3000,
  cors:            true,
  basePath:        '/api',
  bodyParserLimit: '1mb',           // increase for bulk payloads; keep low otherwise
  rateLimit: {                      // built-in sliding-window rate limiter
    windowMs: 60_000,               // 1 minute
    max:      100,                  // 100 requests per minute per IP
  },
});

server
  .registerModel(User)
  .generateRoutes()
  .listen(() => {
    console.log(`Server running on port ${process.env.PORT || 3000}`);
  });
```

## Using an Existing Database

If you already have a database and don't want to recreate the schema, use Drizzle's introspection to pull the schema, then register the resulting table objects with `registerTable()` instead of `registerModel()`.

### Step 1 — Introspect the existing schema

```bash
npx drizzle-kit introspect
```

This reads your live database and writes a `schema.ts` to the folder configured in `drizzle.config.ts`. Example output:

```typescript
// drizzle/schema.ts (auto-generated by drizzle-kit introspect)
import { pgTable, text, varchar, timestamp, boolean } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id:        text('id').primaryKey(),
  email:     varchar('email', { length: 255 }).notNull(),
  password:  varchar('password', { length: 255 }).notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});

export const posts = pgTable('posts', {
  id:        text('id').primaryKey(),
  title:     varchar('title', { length: 300 }).notNull(),
  body:      text('body'),
  published: boolean('published').default(false),
  authorId:  text('author_id'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});
```

### Step 2 — Define Model classes (no `@Field()` needed)

Define your Model classes with lifecycle hooks, `fillable`, `hidden`, etc. You don't need `@Field()` decorators because Crudora won't build the table — it will use the introspected one directly.

```typescript
import { Model } from 'crudora';

class User extends Model {
  static tableName = 'users';
  static hidden    = ['password'];
  static fillable  = ['email', 'password'];

  static async beforeCreate(data: any) {
    data.password = await hashPassword(data.password);
    return data;
  }
}

class Post extends Model {
  static tableName = 'posts';
  static fillable  = ['title', 'body', 'published', 'authorId'];
}
```

### Step 3 — Register with `registerTable()`

Import the introspected table objects and pass them alongside the Model class.

```typescript
import { CrudoraServer } from 'crudora';
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import { users, posts } from './drizzle/schema'; // ← introspected tables

const db     = drizzle(new Pool({ connectionString: process.env.DATABASE_URL }));
const server = new CrudoraServer({ db, dialect: 'postgresql', port: 3000 });

server
  .registerTable(User, users)   // ← uses the existing DB table, no DDL generated
  .registerTable(Post, posts)
  .generateRoutes()
  .listen();
```

`registerTable()` skips `DrizzleTableBuilder` entirely — no schema generation, no `db:push`. The tables are used as-is against the live database.

### Optional: Add `@Field()` for Zod validation

Without `@Field()` decorators, POST and PUT bodies pass through without Zod validation (the database constraints are still enforced at the DB level). Add decorators if you want API-layer validation:

```typescript
import { Model, Field } from 'crudora';

class User extends Model {
  static tableName = 'users';
  static hidden    = ['password'];
  static fillable  = ['email', 'password'];

  @Field({ type: 'uuid', primary: true })
  id!: string;

  @Field({ type: 'string', required: true, unique: true })
  email!: string;

  @Field({ type: 'string', required: true })
  password!: string;
}
```

Then continue using `registerTable(User, users)` — the `@Field()` metadata powers validation while the table object still comes from introspection.

### Summary: `registerModel` vs `registerTable`

| | `registerModel(ModelClass)` | `registerTable(ModelClass, table)` |
|---|---|---|
| Table source | Built from `@Field()` decorators | Pre-built (e.g. from `drizzle-kit introspect`) |
| When to use | New project, schema defined in code | Existing database, schema already in DB |
| `@Field()` required? | Yes (for table building) | No (optional, enables Zod validation) |
| DDL generated? | Yes (via `db:push` / `db:migrate`) | No |

## Drizzle Configuration

```typescript
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema:  './src/db/schema.ts',
  out:     './drizzle',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
});
```

Generate the schema file from your Crudora models, then run migrations:

```bash
# Generate schema.ts from your registered models
npx crudora generate-schema > src/db/schema.ts

# Push schema to the database (development)
npm run db:push

# Or generate a migration file (production)
npm run db:generate
npm run db:migrate
```

## Migration Strategy

### `db:push` vs `db:migrate` — when to use which

| | `db:push` | `db:generate` + `db:migrate` |
|---|---|---|
| What it does | Introspects the live DB and issues DDL to make it match the schema — no files written | Writes a SQL migration file to `./drizzle/`, then applies it |
| Rollback | **None** — changes are applied directly | Possible — migration files are version-controlled SQL |
| Team safety | One developer at a time only | Safe for teams — each developer runs the same migration |
| When to use | Local development / prototyping | Staging and production deployments |

### Recommended workflow

**Development (local only):**

```bash
# 1. Change @Field() decorators in your model
# 2. Regenerate the schema file
npx crudora generate-schema --output src/db/schema.ts

# 3. Push directly to local database — fast, no file overhead
npm run db:push
```

**Production:**

```bash
# 1. Regenerate the schema file after changing models
npx crudora generate-schema --output src/db/schema.ts

# 2. Generate a timestamped SQL migration file
npm run db:generate
# → writes drizzle/0001_<description>.sql

# 3. Review the generated SQL before applying
cat drizzle/0001_<description>.sql

# 4. Apply the migration (run this in CI/CD or at deploy time)
npm run db:migrate
```

> **Never run `db:push` in production.** It applies schema changes immediately without a review step and cannot be rolled back.

### Adding a column safely in production

```bash
# 1. Add the field to your model
@Field({ type: 'string', nullable: true })
bio!: string;

# 2. Regenerate + generate migration
npx crudora generate-schema --output src/db/schema.ts
npm run db:generate

# 3. Inspect the migration — confirm it's an ALTER TABLE ADD COLUMN
cat drizzle/<latest>.sql

# 4. Deploy and run migrate
npm run db:migrate
```

> Add new columns as `nullable: true` or with a `default` first. Adding a `NOT NULL` column without a default to a table with existing rows will fail.

## Logging

### Default Logger

By default, `CrudoraServer` uses a built-in structured JSON logger. Every request gets a `correlationId` automatically:

```json
{"level":"info","time":"2026-01-01T00:00:00.000Z","msg":"POST /api/users","correlationId":"a1b2-...","statusCode":201}
```

### Custom Logger (pino)

```typescript
import pino from 'pino';

const logger = pino({
  level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
  transport: process.env.NODE_ENV !== 'production'
    ? { target: 'pino-pretty' }
    : undefined,
});

const server = new CrudoraServer({
  db,
  dialect: 'postgresql',
  logger,
});
```

### Custom Logger (winston)

```typescript
import winston from 'winston';

const winstonLogger = winston.createLogger({
  level: 'info',
  format: winston.format.json(),
  transports: [new winston.transports.Console()],
});

const server = new CrudoraServer({
  db,
  dialect: 'postgresql',
  logger: {
    error: (msg, ctx) => winstonLogger.error(msg, ctx),
    warn:  (msg, ctx) => winstonLogger.warn(msg, ctx),
    info:  (msg, ctx) => winstonLogger.info(msg, ctx),
    debug: (msg, ctx) => winstonLogger.debug(msg, ctx),
  },
});
```

### Disable Logging

```typescript
const server = new CrudoraServer({ db, dialect: 'postgresql', logger: false });
```

## CORS Configuration

```typescript
// Allow all origins (development)
new CrudoraServer({ db, dialect: 'postgresql', cors: true });

// Allow specific origin
new CrudoraServer({ db, dialect: 'postgresql', cors: 'https://app.example.com' });

// Allow multiple origins
new CrudoraServer({
  db,
  dialect: 'postgresql',
  cors: ['https://app.example.com', 'https://admin.example.com'],
});

// Disable CORS (handle it yourself via server.use())
new CrudoraServer({ db, dialect: 'postgresql', cors: false });
```

## Rate Limiting

Crudora includes a built-in sliding-window rate limiter enabled by default (100 req/min per IP).

### Default (100 req/min)

```typescript
new CrudoraServer({ db, dialect: 'postgresql' });
// equivalent to:
new CrudoraServer({ db, dialect: 'postgresql', rateLimit: { windowMs: 60_000, max: 100 } });
```

### Custom limits

```typescript
new CrudoraServer({
  db,
  dialect: 'postgresql',
  rateLimit: {
    windowMs: 15 * 60_000,  // 15-minute window
    max: 500,               // 500 requests per 15 minutes per IP
    message: 'Rate limit exceeded. Please slow down.',
  },
});
```

### Per-user rate limiting (custom key)

```typescript
new CrudoraServer({
  db,
  dialect: 'postgresql',
  rateLimit: {
    windowMs: 60_000,
    max: 1000,
    // Use authenticated user ID instead of IP when available
    keyGenerator: (req) => req.user?.id ?? String(req.ip ?? 'anon'),
  },
});
```

### Disable (when using proxy-level rate limiting)

```typescript
new CrudoraServer({ db, dialect: 'postgresql', rateLimit: false });
```

**Response headers on every request:**

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Maximum requests allowed per window |
| `X-RateLimit-Remaining` | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the window resets |
| `Retry-After` | Seconds to wait before retrying (only on 429 responses) |

> **Note:** The built-in rate limiter uses in-memory storage — it does not share state across multiple Node.js processes or servers. If you run multiple instances behind a load balancer, use a distributed rate limiter (e.g. Redis-backed) via `rateLimit: false` + a custom middleware.

## Request Body Size

```typescript
// Default: 100KB
new CrudoraServer({ db, dialect: 'postgresql' });

// Larger limit for bulk endpoints
new CrudoraServer({ db, dialect: 'postgresql', bodyParserLimit: '5mb' });

// Explicit byte count
new CrudoraServer({ db, dialect: 'postgresql', bodyParserLimit: 524288 }); // 512KB
```

Requests exceeding the limit are rejected with `413 Payload Too Large` before reaching any route handler.

## Production Checklist

- [ ] `NODE_ENV=production` set
- [ ] `DATABASE_URL` points to a production database (connection pooling enabled)
- [ ] `cors` restricted to known origins (not `true`)
- [ ] `rateLimit` tuned for your traffic; use a distributed limiter behind a load balancer
- [ ] `bodyParserLimit` set appropriately for your largest expected payloads
- [ ] `logger: false` or custom logger configured (no sensitive data in logs)
- [ ] `static hidden` set on all models with sensitive columns (`password`, tokens)
- [ ] Database migrations run before deploying new schema changes (`db:migrate`)
- [ ] Graceful shutdown handler registered (drain connections on SIGTERM)
- [ ] Health check endpoint exposed (`/health`)

### Graceful Shutdown

```typescript
const server = new CrudoraServer({ db, dialect: 'postgresql' });
server.registerModel(User).generateRoutes();

const httpServer = server.listen();

process.on('SIGTERM', async () => {
  httpServer.close(async () => {
    await pool.end();   // close DB connection pool
    process.exit(0);
  });
});
```

## Database Connection Pooling

### PostgreSQL (`pg`)

```typescript
import { Pool } from 'pg';
import { drizzle } from 'drizzle-orm/node-postgres';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,

  // Pool size: keep connections ready for concurrent requests.
  // Rule of thumb: (2 × CPU cores) + effective_spindle_count.
  // For a 4-core server: max = 10–20.
  max: 20,

  // Close idle connections after 30 s to free DB-side resources.
  idleTimeoutMillis: 30_000,

  // Fail fast if the pool is exhausted — avoids indefinite queue buildup.
  connectionTimeoutMillis: 2_000,

  // Enforce SSL in production.
  ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: true } : false,
});

// Monitor pool health
pool.on('error', (err) => {
  console.error('Unexpected DB pool error', err);
});

const db = drizzle(pool);
```

**Sizing guidance:**
- Each Postgres connection consumes ~5–10 MB of RAM on the server.
- Keep `max` at most equal to the DB's `max_connections` divided by the number of app instances.
- Use PgBouncer or `pgcat` in front of Postgres when running many app instances.

### MySQL (`mysql2`)

```typescript
import mysql from 'mysql2/promise';
import { drizzle } from 'drizzle-orm/mysql2';

const pool = mysql.createPool({
  uri:             process.env.DATABASE_URL,
  connectionLimit: 20,     // maximum open connections
  waitForConnections: true,
  queueLimit: 0,           // 0 = unlimited queue (set a value to reject early under overload)
  connectTimeout: 2_000,   // fail if a connection takes longer than 2 s
  ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: true } : undefined,
});

const db = drizzle(pool);
```

**Sizing guidance:**
- MySQL default `max_connections` is 151; leave headroom for admin connections.
- With 3 app instances and `connectionLimit: 20`, peak usage is 60 connections (well under the default).
- Use ProxySQL for connection pooling at scale.

## Security Best Practices

1. **Never expose raw error messages** to clients in production — Crudora returns generic `"Internal server error"` strings, but custom routes should do the same
2. **Rotate secrets regularly** — `JWT_SECRET`, database passwords
3. **Use environment variables** for all credentials — never hardcode
4. **Enable TLS** on the database connection in production (`sslmode=require` for PostgreSQL)
5. **Rate-limit** the API — Crudora's built-in limiter covers single-process deployments; use a distributed Redis-backed limiter for multi-instance setups
6. **Validate input** at every custom route boundary with `getStrictValidationSchema()` or custom Zod schemas
7. **Keep `hidden`** populated for all sensitive fields across all models
8. **Audit lifecycle hooks** — `beforeCreate` is the right place to hash passwords, not application code
